## Overview

`@antelopejs/interface-api-util` holds three helpers for handlers written against `@antelopejs/interface-api`. `assert` checks a condition. `assertValidation` runs an input validator. The `@RateLimit` decorator limits how often a handler runs. Each one reports a failure by throwing an `HTTPResult` from `@antelopejs/interface-api`.

## Choose a guard

| Task                             | Use                                     | Failure behavior                                                                         |
| -------------------------------- | --------------------------------------- | ---------------------------------------------------------------------------------------- |
| Require a resource or permission | [`assert`](#assert)                     | A falsy condition throws the status and message you supply.                              |
| Parse an untrusted request body  | [`assertValidation`](#assertvalidation) | An error thrown by a synchronous validator becomes an HTTP error, status 400 by default. |
| Limit repeated calls             | [`RateLimit`](#ratelimit)               | A request above the fixed-window limit receives 429 before the handler runs.             |

Each helper covers one check. A rate limit does not authenticate a caller, and a TypeScript annotation on a body does not validate the incoming JSON.

## Getting started

Install the package in your module:

```bash
pnpm add @antelopejs/interface-api-util
```

The examples below use the helpers in an AntelopeJS API controller. `findUser`, `findPost`, `removePost`, and `saveUser` stand for your application's data access code. This package does not export them. The Zod examples also need `zod` in your project.

## Reject a bad request

This endpoint needs a non-empty `name` query parameter. With the API module listening, `GET /greet?name=Ada` returns a greeting. `GET /greet` and `GET /greet?name=` return HTTP 400. The example needs no database and no validation library.

```ts docs-check
import { Controller, Get, Parameter } from "@antelopejs/interface-api";
import { assert } from "@antelopejs/interface-api-util";

class GreetingController extends Controller("/greet") {
  @Get("")
  greet(@Parameter("name", "query") name: string | true | undefined) {
    assert(
      typeof name === "string" && name.trim().length > 0,
      400,
      "Name is required",
    );
    return { message: `Hello, ${name}!` };
  }
}
```

`assert` fits a condition you can write as an expression. `assertValidation` fits a schema parser. `RateLimit` bounds repeated requests. The sections below describe each one.

## `assert`

`assert` checks whether a condition is truthy. If the condition is falsy, it throws an `HTTPResult` with the given status code and message.

```typescript
declare function assert(
  condition: unknown,
  code: number,
  message: string,
): asserts condition;
```

| Parameter   | Type      | Description                                      |
| ----------- | --------- | ------------------------------------------------ |
| `condition` | `unknown` | The value to check. A falsy value throws.        |
| `code`      | `number`  | HTTP status code of the error response           |
| `message`   | `string`  | Body of the error response, sent as `text/plain` |

The return type is an `asserts condition` signature, so after the call the compiler narrows `condition` to its truthy type.

### Check that a resource exists

`findUser` stands for your own data access code.

```typescript
import { assert } from "@antelopejs/interface-api-util";
import { HTTPResult } from "@antelopejs/interface-api";

declare function findUser(
  id: string,
): Promise<{ id: string; name: string } | undefined>;

async function getUser(id: string) {
  const user = await findUser(id);
  assert(user, 404, "User not found");

  // `user` is defined here
  return new HTTPResult(200, user);
}
```

### Validate permissions

`findPost` and `removePost` stand for your own data access code.

```typescript
import { assert } from "@antelopejs/interface-api-util";
import { HTTPResult } from "@antelopejs/interface-api";

declare function findPost(
  id: string,
): Promise<{ id: string; authorId: string } | undefined>;
declare function removePost(id: string): Promise<void>;

async function deletePost(postId: string, currentUserId: string) {
  const post = await findPost(postId);
  assert(post, 404, "Post not found");
  assert(
    post.authorId === currentUserId,
    403,
    "Not authorized to delete this post",
  );

  await removePost(postId);
  return new HTTPResult(200, { deleted: true });
}
```

## `assertValidation`

`assertValidation` runs a synchronous validator on an input value. If the validator throws, `assertValidation` catches the error and throws an `HTTPResult` instead. It does not await a promise. A validator that returns a promise gets the promise back unchanged, and a rejection of that promise is not converted. Use a synchronous validator such as Zod's `parse`, not `parseAsync`.

```typescript
import type { HTTPBody } from "@antelopejs/interface-api";

declare function assertValidation<T, Input = unknown>(
  body: Input,
  validator: (body: Input) => T,
  errorFunc?: (err: unknown) => HTTPBody | undefined,
  code?: number,
): T;
```

| Parameter   | Type                                      | Default | Description                                             |
| ----------- | ----------------------------------------- | ------- | ------------------------------------------------------- |
| `body`      | `Input`                                   |         | The input value to validate                             |
| `validator` | `(body: Input) => T`                      |         | A function that returns the validated value or throws   |
| `errorFunc` | `(err: unknown) => HTTPBody \| undefined` |         | Maps the thrown error to the body of the error response |
| `code`      | `number`                                  | `400`   | HTTP status code of the error response                  |

TypeScript infers `Input` from `body`, with no constraint. When you write only `assertValidation<T>(...)`, `Input` is `unknown`. The validator receives the body at type `Input`, so a body typed `Buffer` reaches a `(body: Buffer) => T` validator without a cast. A validator that accepts a wider type, such as Zod's `parse(data: unknown)`, always fits. A validator that accepts a narrower type than the body does not compile. For example, a `(body: string) => T` validator does not accept a `string | Buffer` body. The exception is a body typed `any`, which fits every validator, so the compiler then does not check the validator's parameter type. When the validator's parameter has no annotation, a literal body such as `"lit"` gives it the widened type `string`.

```ts docs-check
import { Controller, Post, RawBody } from "@antelopejs/interface-api";
import { assertValidation } from "@antelopejs/interface-api-util";

function parseJsonObject(body: Buffer): Record<string, string> {
  const parsed: unknown = JSON.parse(body.toString());
  if (typeof parsed !== "object" || parsed === null) {
    throw new Error("Expected a JSON object");
  }
  return Object.fromEntries(
    Object.entries(parsed).map(([key, value]) => [key, String(value)]),
  );
}

class ImportController extends Controller("import") {
  @Post("")
  create(@RawBody() body: Buffer) {
    return assertValidation(body, parseJsonObject);
  }
}
```

On success, the function returns the validated value. On failure, it throws an `HTTPResult` with status `code`. Without `errorFunc`, the body is `String(err)`. With `errorFunc`, the body is its return value. A string is sent as `text/plain`, any other `HTTPBody` as JSON, and `undefined` as an empty `text/plain` body.

### Validate with `zod`

`zod` and `saveUser` belong to your project. This package depends on neither, so the two Zod examples are not compiled with the docs.

```typescript fragment
import { assertValidation } from "@antelopejs/interface-api-util";
import * as z from "zod";

const createUserSchema = z.object({
  name: z.string().min(1),
  email: z.string().email(),
});

function createUser(requestBody: unknown) {
  const { name, email } = assertValidation(requestBody, createUserSchema.parse);

  // `name` and `email` are typed strings here
  return saveUser({ name, email });
}
```

### Custom error formatting

Pass an `errorFunc` to set the body of the error response. This example also changes the status to 422.

```typescript fragment
import { assertValidation } from "@antelopejs/interface-api-util";
import * as z from "zod";

const schema = z.object({ age: z.number().min(18) });

function validateAge(requestBody: unknown) {
  return assertValidation(
    requestBody,
    schema.parse,
    (err) => {
      if (err instanceof z.ZodError) {
        return { errors: err.issues.map((e) => e.message) };
      }
      return { errors: [String(err)] };
    },
    422,
  );
}
```

## `RateLimit`

`@RateLimit` counts requests per key and per decorated handler, in a fixed time window held in process memory. A key's window starts with its first request. It is not aligned to the clock minute. Once the count exceeds `limit` within `windowMs`, the guard throws an `HTTPResult` with status `429` and a `Retry-After` header, and the handler does not run.

An allowed request adds `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` to `context.response`. A rejected request carries the same headers on the thrown response. `X-RateLimit-Reset` is the end of the window as a UNIX timestamp in seconds. `Retry-After` is the delay until then, in seconds. Both are rounded up. If a handler returns a new `HTTPResult` instead of `context.response`, whether the headers survive depends on the API module. Return the context response to keep them.

```typescript
import type { MethodDecorator } from "@antelopejs/interface-core/decorators";
import type { RateLimitOptions } from "@antelopejs/interface-api-util";

declare const RateLimit: (
  limit: number,
  windowMs: number,
  options?: RateLimitOptions,
) => MethodDecorator;
```

`MethodDecorator` is the type from `@antelopejs/interface-core/decorators`, not the global TypeScript type of the same name.

| Parameter  | Type               | Description                                          |
| ---------- | ------------------ | ---------------------------------------------------- |
| `limit`    | `number`           | Maximum number of requests allowed per window        |
| `windowMs` | `number`           | Window duration in milliseconds                      |
| `options`  | `RateLimitOptions` | Optional custom key function and `429` response body |

```typescript
import type { RequestContext } from "@antelopejs/interface-api";

interface RateLimitOptions {
  key?: (context: RequestContext) => string | null | undefined;
  message?: string;
}
```

| Option    | Default                                   | Description                                   |
| --------- | ----------------------------------------- | --------------------------------------------- |
| `key`     | `context.rawRequest.socket.remoteAddress` | Returns the key that a request counts against |
| `message` | `"Too many requests"`                     | Body of the `429` response                    |

By default, the guard counts requests per client IP (`context.rawRequest.socket.remoteAddress`). If the socket has no remote address, the key is the string `"unknown"`, which all such requests share. Provide `options.key` to count by user id, API key, or a forwarded header instead. If the custom key function returns a falsy value, such as a missing route parameter, the guard uses the client IP for that request, so those requests do not all count against one key.

Place `@RateLimit` below the route decorator (`@Get`, `@Post`, and the others). Decorators apply from the bottom up, and the route decorator copies the handler's parameter list when it registers the route. A `@RateLimit` written above it would add its guard too late. `@RateLimit` detects this order and throws an `Error` when the class is defined, so the route never runs unprotected.

### Limit by client address

```typescript
import { RateLimit } from "@antelopejs/interface-api-util";
import {
  Controller,
  Get,
  Context,
  RequestContext,
} from "@antelopejs/interface-api";

class UsersController extends Controller("/users") {
  @Get("")
  @RateLimit(100, 60_000)
  list(@Context() context: RequestContext) {
    context.response.setBody({ users: [] });
    return context.response;
  }
}
```

The first 100 requests from one IP within its 60-second window pass, and request 101 receives 429. Each decorated handler has its own counter, so the same IP has a separate count on another handler.

### Limit by a custom key

```ts docs-check
import { RateLimit } from "@antelopejs/interface-api-util";
import { Controller, Post, HTTPResult } from "@antelopejs/interface-api";

class AuthController extends Controller("auth") {
  @Post(":tenant/login")
  @RateLimit(5, 60_000, {
    key: (ctx) => ctx.routeParameters.tenant,
    message: "Too many login attempts, slow down",
  })
  login() {
    return new HTTPResult(200, { ok: true });
  }
}
```

### Choose a deployment strategy

| Deployment                  | What the limiter counts              | What to do                                                                  |
| --------------------------- | ------------------------------------ | --------------------------------------------------------------------------- |
| One process, direct clients | Requests per socket IP by default    | Use the default key when an IP is the intended identity.                    |
| Behind a reverse proxy      | The proxy's socket IP by default     | Supply a key derived from a trusted proxy hop or an authenticated identity. |
| Multiple instances          | Independent counters in each process | Enforce a shared limit at the edge or in a shared store.                    |

Counters reset when the process restarts. At most once per window, on a request, the guard drops every window that has ended. The store therefore holds only keys whose window started within the last two windows.

A client can set `X-Forwarded-For` to any value. A key read from that header without a trusted proxy lets a client evade the limit or create many keys. A stable custom key does not share the in-memory counter across processes.
